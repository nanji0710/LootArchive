## 功能

### 页面与交互

- 我的页：身份卡 + 收藏亮点（最贵 / 最老）+ 功能入口
- 关于页：动态光斑背景 + 检查更新
- 底部三 Tab 切换（首页 / 统计 / 我的）
- 全站液态玻璃按钮（新增物品 / 统计 / 详情 / 回收站 / 分类 / 备份）

### 物品管理

- 便当盒网格首页，首项双列宽 Hero 卡片，半透明状态区分
- 增删改查，字段覆盖名称 / 分类 / 价格 / 存放位置 / 购入日期 / 描述
- 5 种物品状态：在用 / 闲置 / 已出 / 待修 / 丢失；非在用卡片自动半透明，已出 / 丢失不计入任何金额
- 新增物品为单屏「快记」：名称必填、价格必填，分类 / 状态 / 位置 / 日期 / 保修 / 描述收进「更多信息」折叠区；保存后可直接「再记一件 / 拍照补图 / 相册补图 / 撤销」
- 标签随物品保存与展示（新增入口已移除，仅历史数据与备份导入保留）
- 分类横向滚动筛选
- 关键词搜索：名称 / 位置 / 备注 / 标签 + 最近搜索
- 回收站：保留 14 天后自动清理 + 还原 / 彻底删除

### 照片

- CameraX 应用内拍照，支持闪光灯 + 连拍
- 系统相册批量选择
- 详情页全幅水平滚动 + 圆点指示器
- 导入照片 UUID 文件名防冲突

### 资产统计

- 分类资产环形图 (Canvas Donut)
- 分类多维雷达图 (Canvas + TextMeasurer 字体渲染)
- 累计购入额趋势线 (Canvas)
- 月度购入柱状图，≤6 列居中，>6 列横向滚动
- 分类排名（按金额降序）
- 时间筛选：全部 / 近三月 / 近半年 / 近一年
- 仅统计拥有物品（在用+闲置+待修），金额口径 = Σ购入价

### 数据备份

- 一键导出 ZIP（物品 / 分类 / 照片 / 备份记录 + Excel 明细表），默认落到 `Download/LootArchive/`，失败时回退应用私有目录
- 备份记录列表项可直接点击恢复，弹框确认即触发，无需手动选文件
- 恢复为**合并覆盖**语义：主键命中优先、否则按同名匹配，已有条目被备份内容更新，不重复添加；现有数据保留
- 一键导入恢复，自动 ID 映射

### 个性化与设置

- 深色 / 浅色 / 跟随系统
- 保修到期提醒（阈值可调）+ 备份提醒开关
- 缓存清理 + 数据看板
- 单页新手引导（首次启动，可重置）
- GitHub Releases 版本更新检测

## 数据规则

### 概念定义

| 术语 | 条件 | 说明 |
|:--|:--|:--|
| **拥有物品** | `isDeleted=0 AND status IN ('active','idle','repair')` | 实际持有的物品，也是唯一的统计对象 |
| **全部物品** | `isDeleted=0` | 含已出、已丢失，仅用于计数类展示 |
| **已出 / 丢失** | `status IN ('sold','lost')` | 不计入任何金额（售出后即不再计入） |

### 各页面金额汇总规则

| 页面 | 指标 | 公式 | 分类筛选 | 时间筛选 |
|:--|:--|:--|:--|:--|
| **首页** | 当前拥有金额 | Σ拥有购价 | ✅ 同步过滤 | — |
| | 物品总数 | Σ全部未删除物品 | ✅ 同步过滤 | — |
| | 保修待提醒 | Σ未删除且非已出且保修到期≤阈值 | ❌ 全量 | — |
| **统计页** | 资产总值 | Σ拥有购价 | ❌ | 购价部分受影响 |
| | 物品总数 | Σ拥有物品 | ❌ | ✅ |
| | 分类饼图 | Σ拥有购价按分类 | ❌ | 购价部分受影响 |
| | 雷达图 | Top 5 分类购价对比 | ❌ | ✅ |
| | 累计趋势线 | Σ拥有购价按月累计 | ❌ | ✅ |
| | 月度柱状图 | Σ拥有购价按月份 | ❌ | 购价部分受影响 |
| | 分类排名 | Σ拥有购价按分类降序 | ❌ | ✅ |

> **关键设计决策**：金额口径只有一条 —— 拥有物品（在用 / 闲置 / 待修）的购入价之和。已出 / 丢失的物品一律不计入任何金额，也不再提供售出金额与售出日期的录入（v6.12 移除了该机制）。保修提醒排除已出物品。

## 构建

本地构建：

```bash
./gradlew assembleRelease
```

APK 输出：`LootArchive-release-v6.11.0.apk`（约 7.9 MB，arm64-v8a + armeabi-v7a + x86_64，R8 压缩 + 资源缩减）

### 自动构建与发布

推送到 `main` 后 GitHub Actions 会自动跑单元测试、构建 APK；**改了版本号再推送，就会自动打 Tag 并发布 Release**，不用再手动打 Tag。

版本号写在两个地方，改的时候必须同时改，否则 CI 会直接失败：

| 文件 | 字段 |
| --- | --- |
| `app/build.gradle.kts` | `versionCode`、`versionName` |
| `version.json` | `versionCode`、`versionName`、`updateDate`、`updateLog`、`apkDownloadUrl` |

`versionCode` 才是 App 判断「有没有新版本」的依据（App 只比较它的大小），`versionName` 只是给人看的。**它必须比上一版大**，写小了或忘了改都不会提示更新 —— CI 会在发布前拦住这两种情况（回退、或改了版本名却忘了调大 `versionCode`）。

发一个新版本的完整流程：

1. 改上面两处版本号（例如 `6.12.0` / `712`），并把 `version.json` 的 `updateDate` 改成当天日期
2. 把 `version.json` 的 `updateLog` 写成面向用户的更新说明（会原样成为 Release 说明）
3. 把 `apkDownloadUrl` 里的 Tag 目录改成新版本号：`.../releases/download/V6.12.0/LootArchive-release-v6.12.0.apk`
4. 提交并推送 `main`

CI 会构建出正式签名的 Release APK、校验签名指纹、自动打上 `V6.12.0` 标签、发布 Release，并把 APK 挂上去。Tag 名和 APK 文件名都由版本号推导（`V<versionName>` / `LootArchive-release-v<versionName>.apk`），所以不用手写。`updateLog` 会原样作为 Release 说明，保证 App 内「检查更新」的提示和 Release 页一致。

只推提交、没改版本号时，CI 会识别出「Tag 已指向别的提交」并跳过发布并告警，不会把旧版本重新发一遍；同一个版本重复推送则会刷新已有 Release，不会出错。同一分支的构建是串行的，连续推两次不会互相抢 Tag。

发布用的签名密钥存在仓库的 Secret 里，**只需要配一个**：`LOOTARCHIVE_KEYSTORE_BASE64`，内容是 keystore 文件的 base64（`base64 -w0 你的.keystore`）。密码、别名、密钥密码用的是 Android debug keystore 的固定默认值（`android` / `androiddebugkey` / `android`），已经写在 `app/build.gradle.kts` 的签名配置与工作流里；将来换成应用商店的正式密钥时，再补上 `LOOTARCHIVE_KEYSTORE_PASSWORD`、`LOOTARCHIVE_KEY_ALIAS`、`LOOTARCHIVE_KEY_PASSWORD` 三个 Secret 即可覆盖默认值，不用改代码。

缺 `LOOTARCHIVE_KEYSTORE_BASE64` 时 CI 只构建 Debug APK 用于验证能否编译，不会发布 —— 因为用错签名的包无法覆盖安装，老用户升级只能卸载重装并丢数据。**不要把 keystore 提交进仓库**：这是公开仓库，文件一旦进库，任何人都能签出同签名的包冒充你的更新。

CI 里的 Release 构建带 `-x lintVitalRelease`：本项目会命中 lint 自身的一个缺陷（`NullSafeMutableLiveData` 检测器抛 `IncompatibleClassChangeError`），这个与代码无关，所以跳过；本地跑 `./gradlew assembleRelease` 若碰上同样的崩溃，加这个参数即可。
