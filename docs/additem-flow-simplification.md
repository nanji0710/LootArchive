# 「新增物品」流程简化方案

> 基准：`app/src/main/java/com/nanji/lootarchive/ui/additem/AddItemScreen.kt`（585 行）与 `app/src/main/java/com/nanji/lootarchive/ui/additem/AddItemViewModel.kt`（238 行）当前实现（v6.11.0 + 五项剔除后）
> 目标：把「随手记一件东西」从 3 步向导压到 1 屏，只保留一个必填项；不改变已保存数据的语义与统计口径（除新增的「未估值」态）

---

## 0. 结论摘要

| 指标 | 现状 | 新方案 |
| --- | --- | --- |
| 记一件的最少交互 | **5 次**（FAB → 下一步 → 名称 → 价格 → 保存） | **3 次**（FAB → 名称 → 价格 → 保存），价格框 IME「完成」后 **2 次** |
| 必填字段 | 名称 + 价格（分散在两步） | 名称 + 价格（同屏，见决策点 1） |
| 步骤跳转 | 2 次「下一步」（回改再多 2 次「上一步」） | **0 次** |
| 位置输入 | 纯键盘输入整串（如「卧室书桌抽屉」） | 联想 chip 一次点选，仍可自由输入 |
| 连续录 N 件 | N × 5 次交互，逐件重填 | 首件 3 次，其余每件 2 次（继承分类/位置/日期） |
| 误存 | 无撤销，只能进详情页删除 | 保存后动作条「撤销」 |

> 实施说明（v6.12 已落地）：决策点 1 选择「价格保持必填」，未估值态不做——统计基准是「每个物品的价值」，空价格会直接污染该基准。

## 1. 现状取证（代码事实）

### 1.1 三步向导
- 步骤状态 `var currentStep by remember { mutableIntStateOf(0) }`（`AddItemScreen.kt:62`），步骤指示点为三个圆点 + 连接线（`:148-173`）
- Step 0「照片」（`:198-291`）：照片缩略图（`:203-238`）、「拍照」（`:252-262`）、「从相册选择」（`:263-272`）、「下一步 →」（`:281-290`）
- Step 1「📝 详情」（`:294-455`）：名称（`:297-307`）、分类 10 个 chip 每行 3 个（`:311-340`）、状态 5 chip（`:343-363`）、售出收益（仅「已出」显示，`:366-402`）、价格（`:406-418`）、描述（`:421-430`）、「← 上一步 / 下一步 →」（`:437-452`）
- Step 2「📍 位置与保修」（`:458-547`）：存放位置（`:460-469`）、购入日期行→轮盘（`:472-487`、`:559-567`）、保修天数 + 到期日（`:489-517`）、「← 上一步 / 完成保存 ✓」（`:524-544`）
- 步骤标题文案切换（`:183-193`）

### 1.2 必填与校验（真正的摩擦点）
- 名称必填：`AddItemViewModel.kt:174-177` →「请输入物品名称」
- 价格必填：`AddItemViewModel.kt:178-182`，`price == null || price < 0` →「请输入有效价格」
- **陷阱**：顶部「保存」按钮常驻在任意步骤（`AddItemScreen.kt:129-138`），但在 Step 0 点击它只会得到「请输入物品名称」错误卡片（`:175-182`），而名称输入框在第 1 步（`:297`）—— 用户必须先点「下一步 →」才能填
- 分类标题写作「所属分类 *」（`:312`）却**不校验**：未选时静默归入「其他」（`AddItemViewModel.kt:185-191`），标记与行为不一致
- 价格输入框无 `keyboardOptions`（`:406-417`）→ 弹出通用键盘，需手动切数字

### 1.3 一次性、无后路
- 离开页面即 `resetForm()`（`AddItemScreen.kt:77-79` → `AddItemViewModel.kt:57-62`）→ **无草稿**，误触返回即白填
- 保存成功即 `onNavigateBack()`（`:87`）→ 无「再记一件」「撤销」「补照片」入口

### 1.4 已有能力（可直接复用，无需新建数据通路）
- `ItemRepository.addPhotosForItem(itemId, photoFiles)`（`ItemRepository.kt:180-189`）→ 保存后补照片
- `ItemRepository.updateItem(item)`（`ItemRepository.kt:101`）、`addPhoto/addPhotos`（`:167-169`）
- `ItemRepository.saveItemWithPhotos`（`:139-163`）新建/编辑自动分流，事务内原子写
- `util/LocationSuggestions.kt`（25 行，7 房间 24 个位置 + `flatList`）**当前全仓库 0 引用**
- 注意：`addPhotosForItem` 的 `sortOrder` 从 0 开始编号（`:181-187`），补照片到已有照片的物品会与现有序号冲突 → 调用前需用 `itemPhotoDao.getPhotosByItemIdOnce(itemId).size` 作为起始序号

### 1.5 基建现状
- 项目内 **无任何 Snackbar 使用**（`Snackbar` / `SnackbarHostState` 在 `app/src/main` 0 命中）→ 保存后的动作条需要自研（可复用液态玻璃 `LiquidGlassButton` + `layerBackdrop`）或引入 Material3 `SnackbarHost`
- 已有的日期选择器：`ui/component/WheelDatePickerDialog`（`AddItemScreen.kt:560-583` 使用）

## 2. 现状最少操作路径（记一件「充电宝 ¥99」，名称与价格都已知）

1. 首页点 FAB「新增物品」
2. Step 0 点「下一步 →」（`AddItemScreen.kt:281-290`）
3. 点名称框并输入（`:297-307`）
4. 点价格框 → 键盘切数字 → 输入（`:406-417`）
5. 点顶部「保存」（`:129-138`）

**合计 5 次交互**，其中 1 次是纯跳步、1 次是键盘切换；若还要分类/位置/日期/保修，再加 2 次跳步与 4 处输入。

## 3. 新方案：一步主表单 + 折叠「更多信息」+ 保存后动作条

### 步骤 A（唯一必走）「快记」— 一屏搞定
- **界面**：照片横向缩略条（默认空，右侧「拍照」「相册」两个小按钮）→ 名称输入框（自动聚焦）→ 价格输入框（`¥` 前缀，数字键盘，必填）→ 顶部常驻「保存」
- **输入**：
  - 名称（必填）
  - 价格（必填，见决策点 1）
  - 照片（选填，可留空，之后从动作条补）
- **产出**：一条 `ItemEntity` —— `status="active"`、`categoryId="其他"`、`purchaseDate=今天`、`purchasePrice=输入值`、`name.trim()`；照片写入 `ItemPhotoEntity`
- **交互**：FAB → 输入名称 → 输入价格 → 保存（3 次）；价格框 IME「完成」→ 直接保存（2 次）
- **相比现状省掉**：2 次步骤跳转、「必须先下一步才能填名称」的陷阱

### 步骤 B（可选）「更多信息 ▾」展开区
- **界面**：主表单下一个折叠区（`AnimatedVisibility`，项目已用），默认收起
- **输入与产出**：

| 字段 | 输入形式 | 产出 |
| --- | --- | --- |
| 分类 | 单行横向滚动 chips，默认「其他」 | `categoryId` |
| 状态 | chips（默认「在用」，折叠后不占屏） | `status` |
| 存放位置 | 联想 chips（`LocationSuggestions.flatList` + 最近使用）＋自由输入 | `storageLocation` |
| 购入日期 | 默认今天，行内「今天 / 昨天 / 选择日期」 | `purchaseDate` |
| 保修 | 开关 + 快捷时长（7 天 / 30 天 / 6 个月 / 1 年 / 2 年）＋「自定义」填天数 | `warrantyPeriodDays` / `warrantyExpiryDate`（沿用 `autoCalcWarranty()`，`AddItemViewModel.kt:136-144`） |
| 描述 | 多行（3-6 行） | `description` |

- **交互**：展开 1 次 + 每字段 1 次点选
- **相比现状省掉**：状态 5 个 chip 的常驻噪音、保修「填天数 + 可能再点到期日」、日期轮盘 3 次点击（默认今天）

### 步骤 C（可选，保存后）「动作条」
- **界面**：保存成功后在底部浮出轻量条（3 秒自动消失）：「已保存 · 再记一件 · 补照片 · 撤销」
- **输入与产出**：

| 动作 | 行为 | 产出 |
| --- | --- | --- |
| 再记一件 | 清空 名称/价格/照片/描述，**保留 分类/位置/购入日期** | 连续录入下一条 |
| 补照片 | 直接进拍照或相册 → `addPhotosForItem(itemId, files)`（`ItemRepository.kt:180`，注意 `sortOrder` 起始序号） | 为刚保存的物品补图，无需进编辑向导 |
| 撤销 | `softDeleteItem(itemId)`（`ItemRepository.kt:103`） | 误存回滚 |

### 编辑模式
沿用同一屏：`initEditMode()`（`AddItemViewModel.kt:64-93`）不变，「更多信息」默认展开（编辑时字段多）。

## 4. 操作数对比

| 维度 | 现状 | 新方案 | 差值 |
| --- | --- | --- | --- |
| 最少交互（记名称 + 价格） | 5 次 | 3 次（价格框 IME 提交 2 次） | −40% ~ −60% |
| 步骤跳转 | 2 次「下一步」/ 回改再 2 次 | 0 | −2 ~ −4 次 |
| 必填项 | 2 个，分散在两步 | 2 个，同屏 | 少 2 次跳步 |
| 位置输入 | 手动输整串 | 联想 chip 1 次 | 键盘输入 ≈ −100% |
| 购入日期 | 点击 → 轮盘 → 确定 | 默认今天，改时 1 次 | −2 次 |
| 保修 | 天数框 + 可能再选到期日 | 1 次点选快捷时长 | −1 ~ −2 次 |
| 状态选择 | 常驻 5 chip | 折叠，默认在用 | 视觉噪音 −5 chip |
| 照片 | 第 0 步强制面对 | 顶部缩略条，可后补 | −1 步 |
| 连续录 N 件 | N × 5 次，逐件重填 | 3 + (N−1) × 2 次 | 10 件：50 → 21 次 |
| 误存恢复 | 无 | 「撤销」 | 新增 |

## 6. 需要你确认的决策点

1. **价格留空的语义** —— 已决策（2026-10-12）：**保持价格必填**，不做未估值态。
   - 理由：本 App 的唯一基准是「统计每个物品的价值」，空价格会让统计口径失去意义；「估一个数」比「留空」更符合该基准。
   - 备选（本期不采用）：① `0.0` 表示未估值（零 schema 变更）；② 新增 `isValued: Boolean` 列（DB 迁移 + 备份协议升级）。
2. **购入日期默认今天**：会让趋势线/月度柱状图覆盖到这些物品（现状留 null 会被时间筛选排除），但可能不够准确 → 建议默认今天 + 显眼可改
3. **动作条形式**：自研液态玻璃底栏（与现有 UI 一致，代码略多）vs Material3 `SnackbarHost`（代码少，风格不一致）
4. **描述的位置**：留在「更多信息」折叠区（保持主表单极简），不上移到主表单

## 7. 明确不做

- 扫码 / 条码识别自动填价格、发票 OCR、AI 估价（外部依赖且与「价值统计」基准冲突：错误估值比未估值更糟）
- 表格批量导入、多选批量新建
- 模板系统（可按「再记一件」的字段继承替代）

## 8. 验收与回归

- **编译**：`:app:compileDebugKotlin` + `:app:testDebugUnitTest`
- **装机走查**（ADB 已连接）：① 只填名称保存 → 提示「请输入有效价格」；② 名称 + 价格保存 → 首页出现该物品；③ 保存后「拍照补图 / 相册补图」→ 详情页出现照片；④ 「再记一件」→ 分类/位置/日期已继承；⑤ 「撤销」→ 物品进回收站；⑥ 编辑已有物品 → 各字段回填正常；⑦ 状态改「已出」→ 金额不再计入（首页与统计页数值同步下降）
- **不得回归**：顶部「保存」、照片压缩（`PhotoUtil`，最长边 1280 / JPEG 70）、`saveItemWithPhotos` 事务语义、`resetForm` 的清理（避免上次数据串入新表单）
